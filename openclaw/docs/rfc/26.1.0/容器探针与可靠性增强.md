# 1. 概述

## 1.1 简介

在一体机部署场景下，大部分环境无Kubernetes支持，需通过Docker部署提供探针与增强能力。当前OpenClaw缺乏自愈机制，当进程异常退出或容器卡死时需人工介入，影响服务可靠性。本提案提供标准化容器健康监控与可靠性增强方案，包括Docker Compose部署支持（含自动重启策略）、容器入口脚本健康检查、进程监控与自动恢复机制，确保OpenClaw Agent在生产环境中具备高可用与自愈能力。

## 1.2 动机

当前OpenClaw可靠性方面存在以下核心痛点：

- **无内置健康检测**：无法及时发现Agent异常状态，故障发现滞后
- **异常退出无法自愈**：容器异常退出后无法自动重启，需外部监控系统触发
- **进程卡死无法恢复**：OOM、死锁等场景无法自愈，影响业务连续性
- **多服务协调复杂**：Gateway、SSH等服务需统一启动与管理
- **人工运维成本高**：故障恢复依赖人工介入，无法满足长时间运行要求

**用户案例：**

- 某企业Agent因内存泄漏导致OOM被kill，夜间无人发现，业务中断数小时
- 某边缘设备因网络波动导致Gateway健康检查失败，服务停止后需人工重启
- 某场景Agent进程进入异常状态，健康检查无法识别，业务无响应

**不做此提案的影响：**

- Agent服务中断频繁，无法满足生产环境可用性要求
- 人工运维成本高，企业用户无法接受
- 边缘/无人值守场景难以落地

## 1.3 目标

**目标：**

- 提供标准化docker-compose服务模板，配置自动重启策略与资源限制
- 提供容器入口脚本，统一启动Gateway、插件Worker、SSH等核心服务
- 在容器入口脚本中集成健康检查循环，检测异常后主动退出触发容器重启
- 支持进程优雅终止与清理，避免僵尸进程与资源泄漏

**非目标：**

- 不替代Kubernetes等容器编排平台的健康检查机制（本提案面向无K8s环境）
- 不涉及应用层业务逻辑监控（如Agent对话质量、任务成功率等）
- 不提供分布式高可用方案（如多实例负载均衡）
- 不实现预测性维护（基于历史数据的故障预测）

# 2. 用例分析

## 2.1 用例1：基础健康检测与自动重启

**场景描述：** 标准Docker部署环境下，Agent进程因异常退出，系统自动检测并恢复。

**功能点：**

- 容器入口脚本定期探测Gateway健康端点
- 连续探测失败后主动退出容器，触发Docker自动重启
- Docker Compose配置自动重启策略（unless-stopped）
- 重启事件记录日志

**安全隐私要求：**

- 健康检查不暴露敏感信息

**DFX要求：**

- **兼容性**：Docker环境、Docker Compose支持
- **可靠性**：自动重启成功率高
- **可监控性**：健康检查状态记录日志

## 2.2 用例2：多服务统一启动与管理

**场景描述：** 容器内需同时启动Gateway、claude-mem worker、SSH等多个服务，需统一管理与优雅关闭。

**功能点：**

- 容器入口脚本统一启动所有子服务
- 记录子进程PID，支持批量终止
- 信号捕获与优雅关闭（EXIT trap清理）
- 服务启动失败时记录日志但不阻塞其他服务

**DFX要求：**

- **可维护性**：日志清晰标识各服务状态
- **可诊断性**：异常时可通过日志定位问题服务

## 2.3 用例3：权限降权运行

**场景描述：** 容器以root用户启动，但核心服务以普通用户运行，保障最小权限原则。

**功能点：**

- 容器启动时以root执行初始化操作（修复目录所有权、创建symlink）
- Gateway与Worker服务通过gosu/su-exec降权至普通用户运行
- 无gosu时降级使用su命令

**安全隐私要求：**

- 核心服务不以root运行
- 敏感配置文件权限正确

**DFX要求：**

- **兼容性**：支持gosu、su-exec、su多种降权方式
- **可靠性**：降权失败时有降级方案
- **安全性**：遵循最小权限原则

## 2.4 用例4：容器资源约束

**场景描述：** 防止单个OpenClaw实例占用过多宿主机资源，影响其他服务。

**功能点：**

- Docker Compose配置CPU限制
- Docker Compose配置内存限制
- 资源超限后Docker自动处理

**DFX要求：**

- **可靠性**：资源约束防止实例失控
- **兼容性**：资源限制值可配置

# 3. 方案设计

## 3.1 总体方案

容器探针与可靠性增强采用分层架构，核心组件包括：

```text
┌─────────────────────────────────────────────────────────────────────┐
│                       可靠性增强架构                                 │
├─────────────────────────┬──────────────────────────┬────────────────┤
│      服务启动层          │       健康监控层          │    资源控制层   │
│  Service Launch         │   Health Monitoring      │   Resource     │
│                         │                          │   Control      │
│ ┌─────────────────────┐ │  ┌─────────────────────┐ │  ┌──────────┐ │
│ │ SSH服务启动          │ │  │ Gateway健康探测      │ │  │ CPU限制   │ │
│ │ Gateway启动          │ │  │  - HTTP端点轮询      │ │  │          │ │
│ │ Claude-mem Worker    │ │  │  - 失败计数          │ │  │ 内存限制  │ │
│ │ 启动                 │ │  │  - 阈值触发退出      │ │  │          │ │
│ │ 初始化修复           │ │  │                        │ │  │ 自动重启  │ │
│ │ (doctor --fix)       │ │  │ 进程清理              │ │  │          │ │
│ │ └─────────────────────┘ │  │  - EXIT trap         │ │  └──────────┘ │
│ │                         │  │  - PID批量终止        │ │               │
│ │ 权限降权                │  │                        │ │               │
│ │ (gosu/su-exec/su)      │  │ 日志记录              │ │               │
│ │                         │  │  - 时间戳标记         │ │               │
│ │                         │  │  - 状态变更记录       │ │               │
│ └─────────────────────────┴──────────────────────────┴───────────────┘
│                               │
│                               ▼
│               ┌───────────────────────────────┐
│               │      异常恢复闭环流程           │
│               │                               │
│               │  健康探测失败 -> 失败计数累加   │
│               │       -> 达到阈值 -> 脚本退出   │
│               │       -> Docker自动重启容器    │
│               │       -> 服务重新初始化        │
│               │       -> 健康探测恢复          │
│               └───────────────────────────────┘
```

**核心设计思路：**

1. **统一入口**：容器入口脚本作为单一入口，统一管理所有子服务生命周期
2. **健康闭环**：Gateway HTTP健康探测 → 失败计数 → 主动退出 → Docker重启 → 服务恢复
3. **优雅关闭**：EXIT信号捕获 → 批量终止子进程 → 资源清理
4. **权限分离**：root初始化 + 普通用户运行核心服务

## 3.2 技术选型

### 3.2.1 健康检查方案对比

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| Docker HEALTHCHECK指令 | 原生支持，docker ps可查看 | 仅容器级，需Dockerfile配置 | 可作为补充 |
| 容器入口脚本循环探测 | 集成服务管理，退出即触发重启 | 脚本自身需健壮 | **采用** |
| 外部守护进程 | 功能强大 | 增加部署复杂度 | 放弃（保持轻量） |

### 3.2.2 权限降权方案对比

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| gosu | 安全、轻量、正确处理信号 | 需额外安装 | **优先采用** |
| su-exec | 类似gosu，Alpine常用 | 兼容性不如gosu | 备选方案 |
| su | 系统自带，无需安装 | 信号处理不完善 | 降级方案 |

### 3.2.3 放弃方案说明

| 方案 | 放弃理由 |
|------|----------|
| Kubernetes方案 | 目标场景明确无K8s，保持轻量 |
| 独立Watchdog容器 | 增加部署复杂度，当前单容器方案足够 |
| 分布式高可用 | 单机场景不适用，超出范围 |
| AI预测性维护 | 复杂度高，当前阶段不必要 |

```yaml
services:
  openclaw:
    image: openclaw:version

    user: root
    restart: unless-stopped
    
    # 资源配置
    deploy:
      resources:
        limits:
          cpus: "4"
          memory: 8G
    
    # 存储挂载
    volumes:
      - ./config:/home/node/.openclaw
      - openclaw-skills:/home/node/.openclaw/skills
    
    # 端口映射
    ports:
      - "8080:8080"
      - "8081:8081"
    
    # 环境变量

      - HOME=/home/node
      - OPENCLAW_HOME=/home/node/.openclaw
      - OPENCLAW_GATEWAY_PORT=8080
      - HEALTH_CHECK_PORT=8080
      - HEALTH_CHECK_INTERVAL=30
      - HEALTH_CHECK_FAILURE_THRESHOLD=3
      - OPENCLAW_GATEWAY_TOKEN=<token>
      - ANTHROPIC_API_KEY=<key>
      - OPENAI_API_KEY=<key>
    
    # 容器入口命令
```

**关键配置说明：**

|--------------------------------|------|----------------|
| restart: unless-stopped        | 容器异常退出后自动重启 | unless-stopped |
| user: root                     | 容器以root启动，便于初始化 | root           |
| cpus: "2"                      | CPU使用上限 | 2核             |
| memory: 4G                     | 内存使用上限 | 4GB            |
| HEALTH_CHECK_INTERVAL          | 健康探测间隔（秒） | 30             |
| HEALTH_CHECK_FAILURE_THRESHOLD | 连续失败阈值 | 3              |

### 3.3.2 容器入口脚本设计

**脚本核心流程：**

```bash
#!/bin/bash
# 1. 环境变量初始化
HEALTH_CHECK_PORT=${HEALTH_CHECK_PORT:-8080}
HEALTH_CHECK_INTERVAL=${HEALTH_CHECK_INTERVAL:-30}
HEALTH_CHECK_FAILURE_THRESHOLD=${HEALTH_CHECK_FAILURE_THRESHOLD:-3}

# 2. 目录所有权修复
mkdir -p /home/node/.openclaw/data/.claude-mem/logs
chown -R node:node /home/node/.openclaw/data
chown -R node:node /home/node/.claude

# 3. 启动SSH服务
(/home/node/.openclaw/ssh/start_sshd.sh) &

# 4. 运行启动项修复
node /app/dist/index.js doctor --fix
chown -R node:node /home/node/.openclaw

# 5. 启动Gateway（降权运行）
if [ "$(id -u)" = "0" ]; then
    (gosu node bash -c "node /app/dist/index.js gateway --port $OPENCLAW_GATEWAY_PORT --bind lan --allow-unconfigured ...") &
else
    (bash -c "node /app/dist/index.js gateway --port $OPENCLAW_GATEWAY_PORT --bind lan --allow-unconfigured ...") &
fi

# 6. 启动claude-mem worker（降权运行）
if [ -f "$CLAUDE_MEM_WORKER" ]; then
    (gosu node bash -c "bun $CLAUDE_MEM_WORKER ...") &
fi

# 7. 记录PID
save_pids

# 8. 健康检查循环
failure_count=0
while true; do
    sleep "$HEALTH_CHECK_INTERVAL"
    if wget -q --spider --timeout=10 "http://127.0.0.1:${HEALTH_CHECK_PORT}/health"; then
        failure_count=0
    else
        failure_count=$((failure_count + 1))
        if [ "$failure_count" -ge "$HEALTH_CHECK_FAILURE_THRESHOLD" ]; then
            exit 1  # 触发Docker重启
        fi
    fi
done
```

**进程管理设计：**

```text
┌─────────────┐
│  health_    │
│  monitor.sh │ (PID 1, 容器主进程)
│  (root)     │
└──────┬──────┘
       │ fork
       ├──► ┌─────────────┐
       │    │  sshd       │
       │    │  (root)     │
       │    └─────────────┘
       │
       │ fork + gosu node
       ├──► ┌─────────────┐
       │    │  Gateway    │
       │    │  (node用户) │
       │    └─────────────┘
       │
       │ fork + gosu node
       └──► ┌─────────────┐
            │  claude-mem │
            │  worker     │
            │  (node用户) │
            └─────────────┘
```

**优雅关闭机制：**

```bash
# EXIT信号捕获
cleanup() {
    echo "[Health Monitor] Shutting down services..."
    # 依次发送TERM、KILL信号终止所有子进程
    for sig in TERM KILL; do
        for pid in $(cat /tmp/health_monitor_pids); do
            kill -$sig $pid 2>/dev/null
        done
        sleep 1
    done
    rm -f /tmp/health_monitor_pids
}
trap cleanup EXIT
```

### 3.3.3 健康检查循环设计

**探测逻辑：**

```text
┌─────────┐     ┌─────────┐     ┌─────────┐     ┌─────────┐
│ 等待间隔  │     │ HTTP探测 │     │ 结果判断 │     │ 失败处理 │
│ (30s)   │ --> │ Gateway │ --> │ 成功/失败│ --> │ 计数/退出│
│         │     │ /health │     │         │     │         │
└─────────┘     └─────────┘     └─────────┘     └─────────┘
                                      │
                    ┌─────────────────┼─────────────────┐
                    ▼                 ▼                 ▼
                 成功               失败              连续失败
                 │                  │              达阈值
                 ▼                  ▼                 ▼
              重置计数            计数+1            exit 1
              failure=0          记录日志         触发Docker
                                                    重启
```

**探测参数：**

| 参数 | 说明 | 默认值 | 可配置 |
|------|------|--------|--------|
| 探测间隔 | 两次探测之间等待时间 | 30秒 | 是（环境变量） |
| 超时时间 | 单次探测最大等待 | 10秒 | 否 |
| 失败阈值 | 连续失败多少次后退出 | 3次 | 是（环境变量） |
| 探测目标 | Gateway健康端点 | /health | 否 |

## 3.4 安全隐私与DFX设计

### 3.4.1 安全设计

- **权限分离**：容器以root启动执行初始化，核心服务通过gosu降权至普通用户运行
- **最小权限**：普通用户（node, UID=1000）仅拥有必要的文件访问权限
- **信号安全**：优雅关闭时先发送SIGTERM，超时后发送SIGKILL，避免强制终止导致数据损坏
- **日志保护**：健康检查日志不包含敏感配置信息

### 3.4.2 DFX设计

**兼容性：**

- Docker环境支持
- Docker Compose编排支持
- gosu/su-exec/su多种降权方式兼容

**可维护性：**

- 健康检查参数通过环境变量配置，无需重建镜像
- 日志分级（INFO/WARN/ERROR），便于排查
- 各服务启动状态独立记录，定位问题服务

**可测试性：**

- 健康检查脚本可独立测试（模拟Gateway停止）
- 提供故障注入方法（手动停止Gateway验证恢复）
- 进程清理逻辑可独立验证

**可靠性：**

- 容器异常自动重启（restart: unless-stopped）
- 健康检查超时不阻塞（wget --timeout=10）
- 单服务失败不影响其他服务（后台启动+独立PID管理）

### 3.5.1 编程模型基本设计

### 3.5.2 接口定义与设计

#### 3.5.2.1 health.monitor（健康监控接口）

**接口描述：** 容器入口脚本中的健康检查循环

**接口原型：**

```bash
# 环境变量配置
HEALTH_CHECK_PORT=${HEALTH_CHECK_PORT:-8080}
HEALTH_CHECK_INTERVAL=${HEALTH_CHECK_INTERVAL:-30}
HEALTH_CHECK_FAILURE_THRESHOLD=${HEALTH_CHECK_FAILURE_THRESHOLD:-3}

# 探测逻辑
wget -q --spider --timeout=10 "http://127.0.0.1:${HEALTH_CHECK_PORT}/health"
```

**输入参数（环境变量）：**

| 参数名称 | 输入/输出 | 类型 | 描述 | 取值范围 |
|----------|-----------|------|------|----------|
| HEALTH_CHECK_PORT | 输入 | int | 健康检查目标端口 | 正整数，默认8080 |
| HEALTH_CHECK_INTERVAL | 输入 | int | 探测间隔（秒） | 正整数，默认30 |
| HEALTH_CHECK_FAILURE_THRESHOLD | 输入 | int | 连续失败阈值 | 正整数，默认3 |
| OPENCLAW_GATEWAY_TOKEN | 输入 | str | 网关认证令牌 | 可选 |

**返回结果：**

- 健康：继续循环探测
- 连续失败达阈值：脚本以exit code 1退出，触发Docker重启

#### 3.5.2.2 service.launch（服务启动接口）

**接口描述：** 容器入口脚本中的服务启动逻辑

**接口原型：**

```bash
# SSH服务
(/home/node/.openclaw/ssh/start_sshd.sh) &

# Gateway（降权运行）
(gosu node bash -c "node /app/dist/index.js gateway ...") &

# Claude-mem worker（降权运行）
(gosu node bash -c "bun $CLAUDE_MEM_WORKER ...") &
```

**启动服务列表：**

| 服务 | 启动方式 | 运行用户 | 说明 |
|------|----------|----------|------|
| SSH | 后台启动 | root | 通过start_sshd.sh启动 |
| Gateway | 后台启动 + gosu降权 | node | 核心服务，健康检查目标 |
| Claude-mem worker | 后台启动 + gosu降权 | node | 内存插件Worker |
| Doctor修复 | 同步执行 | root | 启动前配置修复 |

# 4. 缺点和风险

## 4.1 潜在风险

| 风险项 | 风险描述 | 影响等级 | 应对措施 |
|--------|----------|----------|----------|
| 误判健康状态 | Gateway暂时无响应（如GC暂停）导致不必要重启 | 中 | 合理设置阈值（默认3次），避免瞬态问题 |
| 脚本单点故障 | 入口脚本自身异常导致容器退出 | 低 | 脚本逻辑简单，Bash稳定性高 |
| 频繁重启 | 持续性故障导致频繁重启 | 中 | Docker restart策略配合宿主机监控 |
| 数据丢失 | 重启导致进行中的任务数据丢失 | 中 | 优雅终止给予一定清理时间 |
| 子进程泄漏 | 异常情况下子进程未被正确清理 | 低 | EXIT trap + PID文件管理 |

## 4.2 负面影响

- **重启延迟**：服务重启期间（数秒到数十秒）不可用
- **运维复杂度**：增加Docker Compose部署文件配置项
- **日志量**：健康检查定期记录日志，增加日志量

## 4.3 实现成本

- **开发工作量**：容器入口脚本设计、Docker Compose模板配置
- **测试验证**：故障注入测试、长时间稳定性测试
- **维护成本**：跟进Gateway接口变更、健康检查逻辑优化

## 4.4 兼容性考虑

- 与镜像发布特性联动，镜像内置入口脚本
- 与安全沙箱特性兼容，健康检查在容器内执行
- 升级时保持配置兼容，新增配置项有默认值

# 5. 现有技术

## 5.1 参考项目

### 5.1.1 Docker Restart Policy

- **借鉴点**：容器自动重启机制
- **差异点**：在Docker原生基础上增加应用层健康探测

### 5.1.2 Docker HEALTHCHECK

- **借鉴点**：原生健康检查机制概念
- **差异点**：采用脚本内循环探测替代Dockerfile指令，更灵活

### 5.1.3 systemd

- **借鉴点**：服务自动恢复机制
- **差异点**：容器化部署，使用Docker restart策略替代systemd

## 5.2 技术差异优势

| 维度 | 手动Docker部署 | OpenClaw可靠性增强方案 |
|------|---------------|----------------------|
| 健康检测 | 无 | Gateway HTTP探测 + 自动重启 |
| 自动恢复 | 无 | 探测失败退出触发Docker重启 |
| 服务管理 | 手动启动各服务 | 统一入口脚本管理 |
| 权限控制 | 单一用户运行 | root初始化 + 普通用户运行服务 |
| 进程清理 | 无 | EXIT trap优雅终止所有子进程 |

附录

- **术语表：**
  - **探针（Probe）**：用于检测服务健康状态的机制
  - **健康检查**：定期验证服务是否正常运行的探测操作
  - **优雅终止**：发送SIGTERM信号允许进程完成当前工作后退出
  - **降权运行**：以高权限用户启动，然后切换至低权限用户运行核心服务
  - **gosu**：轻量级的用户切换工具，正确处理信号
